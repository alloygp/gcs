1
review.ts — the source of truth

Every review session is controlled by a single file: src/config/review.ts. It holds three things:

export const PASTEL_BASE = 'https://usepastel.com/link/opjd87ro/#'; // fixed per client, set once export const TICKET_ID = '12345'; // updated each review by Claude export const REVIEW_ITEMS = [ { label: 'Homepage', path: '/', review: true }, { label: 'HOA Management', path: '/hoa-management/', review: true }, ];

PASTEL_BASE never changes — it's the permanent Pastel share URL for this client. TICKET_ID and the REVIEW_ITEMS list are rewritten by Claude via the GitHub API at the start of each review session. Only pages with review: true appear in the widget. If no pages are true, the widget is completely hidden.

2
How Claude updates the file

When an employee asks Claude to set up a review, Claude uses the GitHub REST API — no git credentials, no Terminal, no mounted folders. It does two API calls:

# 1. Read current file to get its SHA (required for update) GET /repos/alloygp/{client}-astro/contents/src/config/review.ts?ref=stg # 2. Write the new file content (base64-encoded) back to stg PUT /repos/alloygp/{client}-astro/contents/src/config/review.ts → message, content (base64), sha, branch: "stg" # 3. Force-sync dev to match stg PATCH /repos/alloygp/{client}-astro/git/refs/heads/dev → sha: <new commit sha>, force: true

A fine-grained PAT scoped to the alloygp org (Contents: read/write) is embedded in the skill. Claude derives the repo name automatically from the client name using the slug convention: {slug}-astro.

3
Vercel picks up the push and deploys

Pushing to the stg branch triggers a Vercel Preview deployment automatically. This is why employees wait 60 seconds after Claude finishes — Vercel needs time to build and deploy the new review.ts. The dev branch is force-synced to the same commit so both branches stay in sync.

4
Widget injection via BaseLayout.astro

The widget lives inside BaseLayout.astro as a single <script is:inline define:vars> block. At build time, Astro bakes the config values directly into the HTML:

// Astro reads review.ts at build time: import { REVIEW_ITEMS, PASTEL_BASE, TICKET_ID } from '../config/review.ts'; // Values get baked into the rendered HTML as inline JS vars: <script is:inline define:vars={{ reviewItems: REVIEW_ITEMS, pastelBase: PASTEL_BASE, ticketIdFromConfig: TICKET_ID }}>

Because the config is baked in at render time, the widget works even inside Pastel's proxy — no external fetch needed. The is:inline flag prevents Astro from bundling the script, which would break Pastel compatibility.

Why not a URL param? Early versions used ?review=TICKETID in the URL. That was dropped because the Pastel link is fixed and can't change each session. Now the ticket ID travels via the deployed file instead.
5
What the client sees

The client opens the fixed Pastel URL (e.g. https://usepastel.com/link/opjd87ro/) and sees the staging site inside Pastel's frame. The widget loads bottom-right and opens automatically with a cover screen. The flow:

Cover screen (intro + start button) ↓ Page checklist (only pages with review: true) ↓ client navigates to each page via sidebar, checks it off Confetti fires when all pages are checked ↓ "Submit review" button appears ↓ Success state — widget closes, submission sent

State (which pages are checked, ticket ID) is saved to localStorage so the client can close and reopen without losing progress. Everything is cleared after submission so the next review session starts fresh.

6
What happens on submit

On submit, the widget POSTs to the Astro API route /api/review-complete with the ticket ID and list of reviewed pages. The API route does two things in parallel:

# 1. Slack notification → #pastel-review channel POST REVIEW_SLACK_WEBHOOK { "text": "✅ Keys-Caldwell review complete — ticket #12345\nPages: Homepage, HOA Management" } # 2. Zendesk ticket comment POST https://{ZENDESK_SUBDOMAIN}.zendesk.com/api/v2/tickets/{ticketId}/comments { "body": "Client completed review. Pages approved: ..." }

All credentials (REVIEW_SLACK_WEBHOOK, ZENDESK_SUBDOMAIN, ZENDESK_EMAIL, ZENDESK_API_TOKEN) are stored as Vercel environment variables on the stg project — never in the codebase.

7
Production guard

The widget checks for PUBLIC_ENV === 'production' at runtime. If that env var is set, the widget never renders — it exits silently at the top of the script. This prevents the widget from accidentally appearing on the live client site. The stg Vercel project must not have this var set.

1
Widget must use is:inline define:vars
External JS bundles are stripped by the Pastel proxy. The entire widget must be inline. define:vars bakes server-side config into the HTML at render time — it wraps the script in an outer IIFE. Never move the widget to a separate .js file or import it as a module.
2
No git merge conflict markers inside the script block
Unresolved conflict markers (<<<<<<< HEAD, =======, >>>>>>>) inside the script block cause a silent JS syntax error. The widget appears in the HTML but never runs. Always resolve merge conflicts cleanly before pushing.
3
Body opacity — widget needs opacity:1 explicitly
global.css has @supports not (view-transition-name: none) { body { opacity: 0; } } — body starts invisible on some browsers. The widget container needs opacity:1 !important in its inline style to counteract inheritance, otherwise it never appears.
4
Confetti must attach to document.body, not the widget wrapper
wrap.innerHTML = html wipes everything inside the wrapper on every render. Attaching confetti particles to the wrapper means they get destroyed the next render cycle. Attach them directly to document.body with position:fixed, and always call launchConfetti() after render(), not before.
5
Confetti z-index must be higher than the panel
Widget panel is z-index: 2147483647. Confetti particles must be 2147483648 or higher, otherwise they render behind the panel and are invisible.
6
"Open page" links use direct paths, not Pastel URLs
Early versions linked to pastelBase + item.path. This caused "invalid-proxy-usage" errors when the Pastel link was stale or malformed. Links now go directly to item.path (same-tab navigation). The client stays inside Pastel's proxy because they loaded the page through Pastel in the first place.
7
Pastel comment mode is undetectable from our JS
We investigated every possible signal — body classes, style tag counts, fixed overlays, PerformanceObserver, localStorage. Nothing changes between Browse and Comment mode from our page's perspective. The blue border lives on Pastel's outer application frame, which is cross-origin. The cover screen Browse mode reminder is the only viable solution.
8
Pastel's own "Finish review" button can't be hidden
Pastel injects its own "Finish review" button into the toolbar. The toolbar is iframe-sandboxed so CSS and MutationObserver both fail. A best-effort CSS rule is in the widget but may not work. If it becomes a problem, ask Pastel support if there's a setting to disable it.
9
Most common reason the widget disappears: PUBLIC_ENV=production on stg
If PUBLIC_ENV=production is set on the stg Vercel project (even under Preview environment), the widget's visibility guard suppresses it entirely. Always check this first when a widget that was working stops appearing. Remove the var — let review: true/false in review.ts control visibility.
10
Google Drive can silently revert files
If another process conflicts with a file open in Google Drive, Drive may revert it. Before assuming Claude's GitHub API push was wrong, check the actual file content on GitHub directly. The push either succeeded (check commit history) or failed with an explicit error — Drive conflicts are a separate issue.
11
Git lock files in Terminal
If Terminal shows "lock file already exists," run:
rm -f .git/HEAD.lock .git/index.lock .git/CHERRY_PICK_HEAD.lock .git/packed-refs.lock
